# Port and environment conventions relevant to Grove

Research checked on 2026-09-23. These are integration conventions, not a standard for assigning stable, per-worktree host ports.

## What can be reused

- `.env` is a widely supported output format for named values, but it has no formal cross-platform specification. Node documents its own dotenv syntax and notes that parsers can differ. Grove can emit simple `NAME=number` lines and preserve unrelated file content, while keeping the *allocation rule* in its own repo configuration. [Node.js environment-variable documentation](https://nodejs.org/api/environment_variables.html)
- Docker Compose reads a project `.env` for interpolation and supports `--env-file`. A Compose service can use `${WEB_PORT}` in a published host-port mapping, so a generated port variable can feed existing Compose files. Compose's `ports`, `environment`, and `env_file` describe container runtime behavior, not worktree slot allocation. Grove can also generate a dedicated local Compose override: its `ports: !override` replaces fixed base mappings, whereas an ordinary added port may leave both mappings active. `!override` requires Compose 2.24.4 or later. [Compose interpolation](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/), [Compose service reference](https://docs.docker.com/reference/compose-file/services/), [Compose merge rules](https://docs.docker.com/reference/compose-file/merge/)
- A `Procfile` declares named processes and commands; Heroku's `web` example passes `$PORT` to its server. It supplies useful precedent for a `PORT` startup variable, but no per-service offset or per-worktree range. [Heroku Procfile](https://devcenter.heroku.com/articles/procfile)
- Dev Container `forwardPorts` and `portsAttributes` identify and label ports for forwarding from containers. They do not assign host port blocks to local Git worktrees or describe which `.env` variable/file an app reads. [Dev Container metadata reference](https://github.com/devcontainers/spec/blob/main/docs/specs/devcontainerjson-reference.md)

## Existing service registries

| Format | What Grove could reuse | Missing for worktree ports |
| --- | --- | --- |
| [Docker Compose](https://docs.docker.com/reference/compose-file/services/) | A well-defined `services` map, named published ports, `environment`, and `env_file`. Best existing registry when the repo actually runs its services in containers. | Published host ports describe container mappings; they do not define a per-worktree slot, service offset, or which host-side env file Grove should edit. An interpolated `${WEB_PORT}` can consume Grove's generated value, but inferring its intent from arbitrary Compose expressions would be unreliable. |
| [Procfile](https://devcenter.heroku.com/articles/procfile) | Portable, simple names for runnable process types and their commands; `web` commonly reads `$PORT`. | It has no structured port, env-file, or offset fields. Process types can include workers that need no port. |
| [Process Compose](https://f1bonacc1.github.io/process-compose/configuration/) | Named local processes, commands, per-process `environment` and `env_file`; useful when a repo already uses it. | Its env files supply values to processes, but the configuration does not specify Grove's worktree allocation or a host-port offset to generate. It is a process-manager format, not a general repo service registry. |
| [npm scripts](https://docs.npmjs.com/cli/v11/using-npm/scripts/) | Existing names and commands in JavaScript packages. | Script names such as `dev` have no defined service/port meaning, and scripts do not declare the target env file or port offset. A monorepo may have several packages with the same script name. |
| [Dev Container metadata](https://github.com/devcontainers/spec/blob/main/docs/specs/devcontainerjson-reference.md) | `forwardPorts` and `portsAttributes` document ports used inside a development container. | These are forwarding hints, not definitions of runnable services or dynamically assigned host ports. |

No reviewed format covers all of Grove's required fields across containerized and host-run applications. Keep the small `worktree.json` service map as the explicit allocation contract. Existing Compose, Procfile, Process Compose, or package scripts can remain the source of startup commands; Grove should generate their consumed env values rather than duplicate those commands. Optional discovery of names from an existing file could be a later convenience, but still needs explicit offset and env destination mapping.

## Startup behavior matters

- **Next.js explicitly cannot use `PORT` from `.env`**: its HTTP server starts before those files are loaded. Its supported choices are the `-p` startup flag or a `PORT` variable in the process environment. Generating `.env` alone therefore does not fix Next.js; a script must invoke `grove port` at startup or load the generated file into the process environment before `next dev`. [Current Next.js CLI documentation](https://nextjs.org/docs/app/api-reference/cli/next#changing-the-default-port)
- Vite's server port is a `server.port` config value (default `5173`). Vite automatically tries another port when the requested one is occupied, unless `server.strictPort` is `true`. Repos using Vite need to wire the generated value into Vite config or a CLI argument, and may want `strictPort` so collisions are visible. Vite loads `.env` after evaluating its config, so direct `process.env` reads in that config do not automatically see a newly written `.env`. [Vite server options](https://vite.dev/config/server-options), [Vite env and modes](https://vite.dev/guide/env-and-mode)

## Git and Grove cleanup are different operations

- `git worktree prune` removes administrative records **only for worktrees whose directories are missing**; it does not inspect clean/empty working directories, merge state, or remote branches. `git worktree remove` removes an existing clean worktree; `--force` allows unclean ones. [Git worktree documentation](https://git-scm.com/docs/git-worktree)
- Grove's `grove cleanup <repo> --merged --yes` is the closest command to the desired cleanup: it selects non-main worktrees whose branch is an ancestor of the detected default remote branch and whose working directory is clean. It does **not** automatically run against every worktree, and `--merged` must be supplied. Grove detects `origin/HEAD`, falling back to `origin/main`, `origin/master`, `origin/develop`, then `origin/trunk`; cleanup uses the local remote-tracking ref and does not fetch first. Its `--dry-run` shows candidates. See [`src/commands/cleanup.ts`](../src/commands/cleanup.ts), [`src/commands/list.ts`](../src/commands/list.ts), and [`src/core/git.ts`](../src/core/git.ts).
- Grove normally moves a selected worktree to trash and then invokes `git worktree prune`; `--no-trash` uses `git worktree remove`. It separately guards uncommitted changes, commits ahead of an upstream, and branches with no upstream that are not merged; noninteractive risky removals are skipped unless `--force` is given. See [`src/commands/cleanup.ts`](../src/commands/cleanup.ts).

## Design consequence

Use Grove's repo configuration for service offsets and destinations, and emit simple port variables to the configured `.env` files after bootstrap. Keep `grove port --service` as the framework-independent source of truth for startup scripts and tools whose port is chosen before `.env` loading. Treat Compose and other existing files as consumers of the generated values, not as a universal service-definition schema.
